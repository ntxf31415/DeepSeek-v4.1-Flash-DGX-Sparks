## 一之二、2026-09-13 优化复测（SparkRing 对照后）

参考 `FujitsuPolycom/sparkring`（同为 GB10 无交换机环网栈，其 V4.1 profile 与本站同构）逐项对照后实施：

| 项 | 结论 | 动作 |
|---|---|---|
| worker packed Engram | **发现真 bug**：3/4 rank `packed=False`（2 次读/查询）；根因 = worker `.env.tp4` 的 `MODEL_DIR` 指向不存在路径，`cmd_pack` 挂到空目录仍报成功 | 修 `cmd_pack`（local 模式挂 `WORKER_MODEL_DIR`）+ `model_src` 加断言；重跑 pack + 重启 |
| Engram 列平衡 | 本站连续行切分**无失衡**（四 rank 各 96.0M 行、读取量相等），SparkRing 的列交织问题不适用 | 不改 |
| `NCCL_SWITCHLESS_RING_ONLY=1` | 本站 ring-only NCCL（LuZ 自建）**不认识该变量**（SparkRing 自有补丁）；通道数已是 4 = 其值 | 不改 |
| 路由/转发 | `ip_forward=1` 已开、路由表仅直连 4 条 fabric 子网、rendezvous 走管理网 → 干净 | 不改 |
| `--max-num-seqs` | 8 → **12**（含 CUDA graph bs=12） | 已改 |

## 二、结论画像

**dsv41 = prefill 王者 + 单流中等 + 高并发中上。**

- **prefill 全面碾压历史方案**：8K 2814 = GLM 的 1.30×、Vision 的 1.69×、LuZ 的 1.87×；100K 3119 = 历史最好 2430 的 1.28×。对 agentic 短平快（大量短 prompt）与长文档冷加载场景是净收益。
- **单流 decode 89.6 = LuZ 的 67%、Vision 的 83%、GLM 的 95%**——V4.1-Flash 参数量级（552B MoE，8B/16B 激活）的单流代价；story 型 29.4 与上游 37.9 同量级，code 型 89.6 是上游单流 2.4×（TP4 vs 其 TP3 + 环网适配的收益）。
- **并发聚合**：c2 反超 Vision OFF 79%，c4-c12 与 Vision 打平；c12 271 = LuZ 444 的 61%——高并发下 LuZ 的 W4A4+DSpark k=7 仍是天花板。
- **thinking ON ≈ OFF**（90.0/72.3 vs 89.6/72.1，c6 +17）——与 Vision 的"免费+高并发档"（c8 +66%）不同，V4.1 的思考模式不改变聚合画像；唯一例外是**散文 +9%**（30.8→33.6 t/s，可预测文本的投机增益）。
- **散文单流 30.8 t/s（OFF）/ 33.6（ON）**：长文本生成是 dsv41 最慢的形态（= Vision 的 73%）；重度散文/创作流量的速度体感会明显低于 Vision-Exp 与 LuZ。
- **长档**：400K 档落后 GLM（其优势域，1.76×），但 900K 可用且 needle 正确；dsv41 胜在中短 prefill 与 1M 满窗可用。

**一句话**：换 dsv41 用单流速度（-17%~-33%）换 prefill 大幅领先（+28%~+87%）——适合 prompt 密集/长输入重读的流量形态；若流量以长对话 decode 为主，LuZ0.4.5 仍是单流/高并发王者。
