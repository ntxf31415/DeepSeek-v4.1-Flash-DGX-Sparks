## 二、上游 ISSUE/PR 调研（按可采纳度排序）

### A. 立即采纳：MiaAI PR #17 — 共享专家 K padding（**无损 +1.1~1.5%**）

- **我们确实踩中**（已核验启动日志）：`DSV41 MXFP8 backend 'b12x' rejected N=5120 K=576`
- 根因：TP4 下共享专家 `down_proj` 的 K = 2304/4 = 576，不是 128 的整数倍 → b12x 拒绝 → 回退 CUTLASS（128×32×128 tile，decode M=6 时把 M 补到 128 → 96256B smem → 每 SM 一块 → **GB10 48 SM 上仅 25% 占用**）→ 实测 **52 GB/s**（该部件可跑 232-238 GB/s）。这是**唯一**被拒的 shape，但存在于全部 40 层。
- 修法：在 `_prepare_block_fp8_as_mxfp8` 之前把 weight 补零到 K=640、scale 补 1；调用时把输入经**常驻零缓冲**补到 640（CUDA graph 需稳定地址）。代价 14 MB/rank。开关 `DSV41_SHARED_PAD_K=1`。
- 实测：`cutlass K=576 58.0us → b12x K=640 17.2us`（-70.3%）；**净 -0.90 ms / 61.3 ms 步 = +1.47% 预测**，稳态实测 prose +1.14% / code +1.51%。
- **无损**：0/30720 元素逐位相同，max|diff|=0。
- ⚠️ 关键注记（作者自述）：**单纯 padding 无收益**（CUTLASS 在 K=640 反而慢 0.7%）——收益全部来自「padded shape 获得 b12x 资格」。本站 `DSV41_MXFP8_BACKEND=b12x` ✓ 适用。

### B. 高价值：MiaAI PR #7 — EP_SIZE=2 等四项（**+10.5%**，质量不变）

| 项 | 机制 | 实测 |
|---|---|---|
| **`EP_SIZE=2`** | EP4 时每 rank 持 96/384 专家、每步随机抽子集；TP 同步 → **步耗时付 4 rank 的最大值**。M=6 时每 rank 不同专家数 ~8.6±2.8 → 最慢 rank 多做 30-45% MoE 工作。EP2 减半 | **NCCL 每步 16.5 → 10.2 ms（-38%）**；all-reduce p90 479→350µs；≥200µs 调用 35(13.0ms)→18(6.2ms)；MoE grouped GEMM 不变（21.6→21.5ms）→ **是 straggler 修复，非带宽修复** |
| `DSV41_CACHE_GIB=4` + `CACHE_WAYS=16` | Engram 行缓存 | 命中率收益 |
| `--min-free-slots-delay 1` | 调度准入 | 恢复第 8 槽 |
| `--enable-deepseek-v4-fp4-indexer` | DSA indexer 的 FP4 kernel | kernel/精度选择 |

- 总计 **+10.5% 均值**（conc1 +15~21%，conc2-4 +7.7~9.5%）；第二套 prompt 交叉验证 +9.8%；**decode step 69.0 → 61.0 ms 中位（-11.6%）**
- **质量不变**：75 个自动评分任务（代码跑隐藏断言/JSON schema/数值/格式/散文退化）逐步做 McNemar 精确检验 → **零任务破坏，p=1.000**；长上下文检索另测 30/30
- **对本站意义最大的是 EP_SIZE=2**——NCCL 是环网的成本中心，-38% 直接打在痛点上

### C. 最高收益但需谨慎：SparkRing PR #267 — SGLang「decoder-tail prefill」（**64K prefill +57%**）

- **这就是「SIRCL 移植」问题的答案**：SparkRing 自己的 **SGLang** V4.1 cycle 配方**不使用 SIRCL**——用的是 decoder-tail prefill + 换掉 pip NCCL
- 机制：V4.1 prefill 原本对全 prompt 跑完 40 层骨干；该配方在**全局 KV 源层之后，晚期 decoder 只处理末尾 128 个 extend token**（每条请求）
- 实测：**64K prefill 2,006 → 3,144 tok/s（+57%）**；20/20 首 token 选择一致 + 20/20 贪心续写一致（有界门禁）
- 另：**替换 pip NCCL 为预加载库**（规避 duplicate-NCCL，与我们用 `EP_SUPPRESS_NCCL_CHECK=1` 同类问题的另一种解法）；启动器做镜像/NCCL 身份校验、单行多 key、不把 key 暴露进 docker args
- 站点侧 6 小时 C8 浸泡：**13,224 请求零失败零挂起**，每波聚合中位 106.7 tok/s，可用内存地板 28.47 GiB；20 分钟门禁 464 请求零失败
- 公共默认 context 262144；站点用 chunk4096 / context430080
- ⚠️ **风险**：decoder-tail 是**近似**（靠门禁一致性背书），须在站内用 needle 梯度 + 质量门禁复验后才可上产

## 三、SIRCL/sparkring 移植评估

**结论：不建议移植 SIRCL；应借鉴其 SGLang 配方的 decoder-tail prefill。**

| 维度 | 事实 |
|---|---|
| SIRCL 是什么 | SparkRing 自研集合通信层，把环上的 collective 排成**两个完美匹配**（0-1/2-3、1-2/3-0），使任何 rank 不必中继他人 collective 数据 |
| 谁在用 | SparkRing 的 **vLLM** 配方（GLM/部分 DS 档）。**其 V4.1 SGLang 配方不使用 SIRCL**（PR #267 明示用 decoder-tail + 换 NCCL） |
| 移植到本站的障碍 | ① SIRCL 是 vLLM 侧集成（持久 RDMA session + graph-replayable command ring），SGLang 侧无对口接口 ② 本站 NCCL 已是 ring-only 且 Tree 已禁用，环内集体已走邻居——SIRCL 的收益面（消中继）在当前 `moe_a2a_backend=none` 下主要落在 MoE all-to-all ③ 与本站 LuZ 谱系 NCCL 分叉，须整链替换 |
| 真正的收益点 | 本站 `moe_a2a_backend=none` → MoE token 搬运与 TP 共用 NCCL 环 → 非邻接 all-to-all 绕环两跳。**PR #7 的 EP_SIZE=2 正是对这个成本中心的直接削减（NCCL/步 -38%）**，成本远低于移植 SIRCL |
| 若要进一步 | 先上 EP2（低风险、已有人验证）；仍不足再评估 SIRCL 级方案 |

## 六、600K 前端上下文评估（2026-09-13）

**场景**：前端按 600K CTX 使用。

**服务端限制（实测）**：`context_length` 1,048,576 · `max_req_input_len` 1,048,570 · KV 池 `max_total_num_tokens` 4,999,936 · `max_running_requests` 12 · 代理 `MAX_CONCURRENCY` 12。

**端到端实测 632K**：needle **PASS**（PELICAN 命中），冷 prefill **430 s / 1472 t/s**，memguard 最低 **5.60 GB** 无 abort。

| 结论 | 依据 |
|---|---|
| **配置够用，无需改** | 服务上限 1M 已涵盖 600K 并留 448K 余量；632K 实测通过 |
| **满长并发 ≈ 8 路** | KV 5M ÷ 600K = 8.3；12 路上限下超出部分由 SGLang retraction 策略抢占，实际落 ~8 |
| **600K 冷 prefill ≈ 5–7 分钟**（真实成本） | 同口径（prefill_distinct）随上下文衰减：200K 2483 → 500K 1913 → **632K 1472** → 900K 1409 t/s，非故障 |
| **c6 回退与本场景基本无关** | benchmark 的 c6 是「400 token 短输出」档；600K 前端 = 长输入 → prefill 主导，而 prefill 全面提升（8K +6.8%，长档耗时 −9~−17.5%）。**回退只存在于「中并发 + 短输出」角落** |
| 若要 12 路满长并发 | 需 KV ≈ 7.2M，当前 5M 无余量 —— **不建议**；8 路满长对个人/小组足够 |

### ⚠️ 600K 前端 vs 当前 `MAX_RUNNING_REQUESTS=12` 的容量冲突

KV 池是**全局共享**的：每个在飞请求占用 `prompt + 生成` 的 token。当前 12 路并发下，**每会话能拿到的 KV 上限 = 5,000,000 ÷ 12 ≈ 417K**，**低于前端声称的 600K**——即：12 路同时在跑时，任一会话涨到 ~417K 就会触发 KV 抢占（`retraction_policy=length`），**够不到 600K**。

| `MAX_RUNNING_REQUESTS` | 满长并发下每会话可用 ctx | 与 600K 前端匹配 | 代价 |
|---:|---:|:--:|---|
| 12（当前） | ≈ 417K | ✗ 差 183K | 保留 c12 384 t/s 的短请求吞吐 |
| **8** | **≈ 625K** | **✓ 刚好覆盖** | 放弃 c12 档，c8 293 t/s 仍在 |
| 12 + KV 提到 7.2M | 600K | ✓ | 当前内存配置下**不可行**（MEM_FRACTION 0.90 已无余量） |

**建议**：若前端确实按 600K 使用（会话会实际涨到数百 K），把 `MAX_RUNNING_REQUESTS` 回调到 **8**——5M ÷ 8 = 625K，正合 600K；代价是放弃 c12 那档（c12 385 t/s 是「12 路短请求」的成绩，长会话场景本就到不了）。若前端只是把上限设成 600K 而实际会话远短，则维持 12 更划算。


## 七、MiaAI PR #3 评估（switchless-ring 支持）

**它解决的是我们没有的故障**：stock TP4 profile 在 4 节点环上 NCCL 初始化失败——

```
NCCL INFO Trees [0] 2/-1/-1->0->-1
RuntimeError: NCCL error: unhandled system error
    at ncclTransportTreeConnect -> ncclCommInitRank
```

根因（PR 自述）：4 节点环上 rank0↔rank2 非直连；NCCL 在 ring 之外**额外建 tree**，而 **RoCE queue-pair 建立不跟随 IP 路由** → tree 永远连不上 → boot 死。

**我们为什么没踩**：日志里同样有 `Trees [0] 2/-1/-1->0->-1` / `Connected all trees`，但我们的 NCCL 补丁把 **Tree 在算法矩阵里置 0**（见 §一），Tree 构造不参与后续 QP 建立，故不触发。

**其 env 契约与我们的对照**：

| 变量 | 我们的 NCCL | 我们当前设置 |
|---|:--:|---|
| `NCCL_ALGO=Ring` | ✓ | 已设 |
| `NCCL_MIN_NCHANNELS=4` | ✓ | 已设 |
| `NCCL_SKIP_TREE_CONNECT` | **✗ 不认得**（它/sparkring 自有补丁） | — |
| `NCCL_SWITCHLESS_RING_ONLY` | **✗ 不认得**（同上） | — |
| `NCCL_IB_SUBNET_PREFIX_LEN=24` | **✓ 支持** | 未设（用默认） |
| `NCCL_P2P_LEVEL=SYS` | **✓ 支持** | 未设（用默认） |

**结论：不需要采纳**。两点价值：
1. **反证我们的手搓适配是必要的**——stock TP4 profile 在 4 节点环上根本起不来，我们踩过的坑别人踩不住就是因为直接失败
2. 它带 323 行 `docs/switchless-ring.md`，可作**路由/校验项对照**，核查我们有无遗漏；另有两个「我们支持但未设」的变量（`NCCL_IB_SUBNET_PREFIX_LEN` / `NCCL_P2P_LEVEL`）可在下次窗口做单变量 A/B（本站 fabric 子网本就是 /24，默认值大概率已等效）

### ③ autotune 竞态 —— 解释了我们的测量方差

**为什么重要**：我们多次观察到同配置下读数跳动（如峰 89.6 vs 92.9 vs 98.6），此前归因于碎片/干扰。**这条给出了另一个机制性解释**——若我们也存在 fp8_gemm autotune 竞态，那单次 boot 的性能有随机性，需要固定 autotune 缓存路径（我们已有 `VLLM_FLASHINFER_AUTOTUNE_CACHE_DIR` 类做法，但 SGLang 侧需确认）。

### C15 — 换 switchless-nccl 构建：**评估后不采用**

- Alex 的 `switchless-nccl` v0.0.1 与本站 LuZ 构建**同为 NCCL 2.30.7**，走不同补丁路线（`SWITCHLESS_RING_ONLY` vs 算法矩阵 Tree=0）；本站路线实测**更彻底**（Tree 在矩阵里=0，而它的 tree 连接函数只是"假装成功"）。

- 换构建需整链替换 + 重新验证，风险大于预期收益。**不采用**；若将来 LuZ 构建出问题，它是一个现成的替代选项（Apache-2.0、有版本化 release）。

### B7 — c6 低点：**已定性为 EP2 的可接受代价**

| 配置 | c4 | c6 | c8 | c12 |
|---|---:|---:|---:|---:|
| EP4（原始） | 210 | 260 | 264 | 271 |
| EP2 | 221 | **237** | 287 | **399** |

c6 从 260 降到 237（−9%），但 c8 +9%、c12 +47%、长档 prefill +9%、peak +3%。**EP2 是全局更优**，c6 一点是同一条曲线上的局部凹陷（可能源于 EP2 下 6 并发恰好落在某种专家分布劣化点）。**维持 EP2，不再追。**

### B8 — hybrid MLA backend：**评估后暂不采用**

magicbear 的做法是 sitecustomize 补丁按 query 长度分流（短 decode → FlashInfer/split-K，长 prefill → SM120 Triton sparse-MLA）。本站现状：`--attention-backend dsv4` 且 `dsv4_prefill_backend=auto`——**SGLang 已内置自动选择**。差异在于其补丁做了更激进的显式分流。考虑到：① 需要新增并验证一个内核分派补丁 ② 本站 prefill 已达 3,238 t/s @100K、decode 峰 100.7，属同类栈前列 ③ 该补丁的正确性只有作者单方面验证 —— **暂不采用**，列为后续 A/B 候选（若将来 prefill 成为瓶颈）。

### B12 — STS 校准表：**实测后确认被上游 bug 阻塞（不可为）**

尝试按步骤执行，得出**引擎级证据**而非推测：

1. 以 `SGLANG_DSPARK_STS_COLLECT_PATH=/state/sts-shards/sts` 启动（该环境变量确已进容器），灌 24 条多样化请求（code/count/散文/JSON/数学/工具），**零 shard 产出**。
2. 查 SGLang 源码定位原因：
   - `dspark_observability.py:936` — `if not self._planner.carries_confidence: return`
   - `dspark_planner.py:210` — `def carries_confidence(self): return self._confidence_head is not None`
   - `dspark_planner.py:124` 的告警原文：**"DSPark STS calibration path given but no confidence head present (static mode / head-less checkpoint); ignoring"**
3. **引擎自身日志给出判决**：
   ```
   --speculative-dspark-sps-table-path feeds the ragged-verify budget scheduler,
   which is off under SGLANG_RAGGED_VERIFY_MODE=static; it will be a no-op.
   ```

**结论**：STS 采集要求 **compact/ragged verify 模式**（该模式才装载 confidence head）。而 compact 模式在 V4.1 + Engram 上触发 `engram target-verify` 断言崩溃（＝ [sglang#39173](https://github.com/sgl-project/sglang/issues/39173)，见 C14）。

→ **B12 与 C14 同源，同样被上游阻塞，当前配置下不可执行。**

⚠️ **附带发现（重要）**：同一条日志说明**我们现役的 SPS 表在 static 模式下也是 no-op**。即：DSpark 的 ragged-verify 排程增益**当前并未生效**（这正是上游 PR#7 声称 +10.5% 的那部分）。SPS 表保留无害（compact 修复后即可生效），但**不应把已有收益归因于它**——本轮实测的 c12/长档提升来自 EP2、Engram 缓存、PR17 与碎片清理。
